# Hook security review

## Review boundary and primary sources

This is an **audit-informed assistant review**, not an independent security audit, a certification, registry admission, or a guarantee of safety. State who reviewed what and what was actually exercised. The official [Uniswap security framework](https://developers.uniswap.org/docs/protocols/v4/security) is voluntary and self-directed; neither a risk score nor its use implies Uniswap Foundation review or endorsement.

Read `CONTRIBUTING.md` (Hook requirements, Fees and author payment, Provided accounting, Optional truncated oracle, and PR review), `SECURITY.md`, the submitted `review.md`, and the actual inherited implementation. Use the [hook-authoring skill](../hook-authoring/SKILL.md) for authoring constraints and the [hook-qualification skill](../hook-qualification/SKILL.md) for commands, environment setup, fork identity, evidence interpretation, and runner diagnosis. Do not maintain a second qualification command sequence here.

Use these primary references for review hypotheses, not as proof that the submitted runtime is safe or vulnerable:

- [Official hooks concepts](https://developers.uniswap.org/docs/protocols/v4/concepts/hooks): address-encoded callbacks and return-delta permissions, hook identity in the full pool key, and lifecycle interception.
- [Official flash accounting](https://developers.uniswap.org/docs/protocols/v4/concepts/flash-accounting) and [unlock callback and deltas guide](https://developers.uniswap.org/docs/protocols/v4/guides/unlock-callback-and-deltas): transient debts/credits and settlement at unlock completion. Initialization is not a balance-changing unlock operation.
- [OpenZeppelin Uniswap v4 Core Audit, August 27, 2024](https://www.openzeppelin.com/news/uniswap-v4-core-audit), scope [v4-core `d5d4957b35750e8cf1f3db5584e77eef4861c21e`](https://github.com/Uniswap/v4-core/tree/d5d4957b35750e8cf1f3db5584e77eef4861c21e). The report fully reviewed its listed new files; specified inherited math libraries were reviewed only as a diff against [v3-core `d8b1c635c275d2a9450bd6a78f3fa2484fef73eb`](https://github.com/Uniswap/v3-core/tree/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/libraries).
- [OpenZeppelin Uniswap v4 Periphery and Universal Router Audit, August 30, 2024](https://www.openzeppelin.com/news/uniswap-v4-periphery-and-universal-router-audit), scope [v4-periphery `df47aa9ba521fc15ffd339dc773d32f5fc4c91fc`](https://github.com/Uniswap/v4-periphery/tree/df47aa9ba521fc15ffd339dc773d32f5fc4c91fc) and [universal-router `4ce107d6387558b97816293fe2c0d4d7c4cadef4`](https://github.com/Uniswap/universal-router/tree/4ce107d6387558b97816293fe2c0d4d7c4cadef4), with the router review focused on V4 integration. The report additionally describes post-audit reverse-mapping changes; it is not an audit of every later revision.

For each historical finding used below, compare the actual dependency pin, audited code, and linked fix diff. Record whether the fix is present, equivalent, absent, or not yet established, plus whether the affected path is reachable. The installer pins core, not the audited periphery/router graph; do not infer that those contracts are dependencies merely because their audit supplies a useful lesson. Published resolution status applies to the report's upstream finding, not automatically to this repository or a deployed manager. Do not label a historical issue a current vulnerability without current-code and consumer-impact evidence.

## Non-negotiable catalogue invariants

Official Uniswap examples describe a broader ecosystem than this catalogue. Review the supported **immutable, single-market `PoolBoundV4`** design, not a generic hook template:

- One concrete hook derives from `PoolBoundLaunchHookBaseV2` with the typed `PoolBoundHookParametersV2` constructor. Optional `PoolBoundTruncatedOracleV2` composes into that same runtime. No proxy, upgrade path, custom companion deployment, externalized principal strategy, or modification of the approved base to make a submission pass.
- Preserve manager-only callbacks, permission bits `0x1afc` under `0x3fff`, one-time registrar binding, exact full-key checks, permanent launch-liquidity custody, collector-only fee collection, and backed fee-only accounting. Donations are not hook fees. External LP participation follows the frozen configuration; it is not a permission to withdraw the permanently held launch positions.
- Pool LP fees remain zero. Static hook rates use the creator's maximum; explicitly dynamic policies use the read-only rate seam within frozen minimum/maximum bounds. These are **hook-delta fees**, not dynamic LP-fee overrides. A nonzero PoolManager protocol fee must reject trading rather than silently add a fee.
- Preserve `floor(amount * rate / 1_000_000)` with full precision and the `int128.max` fee bound. Preserve treasury division order: `denominator == 0 ? 0 : (grossHookFee / denominator) * 125 / 100`, with nonzero denominator `4..10`.
- `authorFeeBps()` matches manifest `developerFeeBps`; `authorId` is a stable identity, not the live payout wallet. Developer allocation occurs once in the downstream fee hub after the bounty and disposition split. No hook-level author payment, sweep, alternate recipient, or recipient-selection seam.
- Review the complete artifact, added selectors, inheritance, assembly, and storage effects. Nonvirtual base callbacks and guards are not a sandbox against a malicious derived runtime.

Submission changes stay under `hooks/<slug>/`, including mandatory `test/Smoke.t.sol`, separate policy suites/fixtures in flat `test/`, and optional successful runner-generated `provenance.json`. New harness capability belongs to a separate maintainer infrastructure change. Use existing test-side quote/configuration, prerequisites and genuine signed hookData seams without qualification-only production getters. Do not relax validation, change dependency pins, alter compiler settings, or split deployment to evade artifact limits.

## Prioritized executable workflow

Produce a scope record, a reachability/authority map, adversarial test evidence, and a findings report. Prioritize unauthorized asset movement and unbacked liabilities before economic manipulation, then liveness and lower-impact correctness. For every hypothesis, identify the reachable entrypoint, attacker capability, precondition, violated invariant, and an observable result before writing a test.

### 1. Freeze the exact review subject

Record the repository commit **and any working-tree differences**, submission slug, source file hashes, inherited/local libraries, manifests, terms, and policy bounds. Read `scripts/upstream.json`, `scripts/protocol-source-pins.json`, `scripts/install-deps.sh`, `foundry.toml`, and the qualification outputs. A provenance HEAD alone does not identify locally adapted sources; file SHA256 pins are not Solidity admission digests.

Bind conclusions to measured creation/runtime artifacts, constructor tuple, compiler/settings, linked code, deployer identity, CREATE2 salt/address and permission bits, full pool key/ID, and reviewed economic configuration. For fork/deployed behavior, include chain ID, block number/hash, manager/oracle/WETH and infrastructure addresses and code hashes. Distinguish the fork venues and historical reference envelope in `contracts/config/robinhood.json`, isolated launch actors created from the external dependency snapshot, and any actual production graph.

Write a small threat-model table: protected asset/authority, authorized actor, attacker capability, trust assumption, and failure impact. Include trader input/output, permanent launch principal, fee claims and settled cash, treasury/owner/developer liabilities, oracle history, author-controller consent, and registry/collector identity. Distinguish arbitrary callers, malicious routers, malicious tokens/dependencies, and privileged actors. Scope inherited code explicitly; exclusions are coverage gaps, not assertions of safety.

### 2. Trace lifecycle, caller identity, and authority

Start with `PoolBoundLaunchHookBaseV2`, `LaunchHookReentrancyGuardV1`, `PoolHookDeployerV1`, the concrete policy, and applicable oracle template. Enumerate **all** external/public selectors, including added functions, fallback/receive behavior, and inherited getters. For each selector, record permitted phase, caller, pool key, state mutation, external calls, and expected rejection.

- Distinguish callback `msg.sender` (the authenticated manager) from the callback's `sender` argument (the manager operation's caller). A router is not necessarily the end user; `tx.origin` and unvalidated `hookData` are not authorization.
- Follow constructor validation → exact core Prepare/registrar registration → authenticated initialization at the planned price → initial liquidity/author-terms authentication → opening completion → trading/collection. Test direct callback calls, wrong manager/registrar/collector, pre-registration/pre-initialization calls, duplicate registration/initialization/opening, and unauthorized fee collection.
- Change each full-key field independently: currency order/identity, fee, tick spacing, and hook address. A token pair or partial key is insufficient. Review ABI/assembly guards for dirty high bits, short returns, malformed tuples, and exact binding to collector, locker, core and hub.
- Match deployed address bits, declared permissions, implemented callbacks, selectors, ABI return lengths and delta permissions. This base has no `beforeInitialize` permission or general swap admission gate; verify its actual `afterInitialize` enforcement instead of assuming a template's gate exists.
- Author payment terms bind after registration/initialization. Test the frozen hub author rate before the **first liquidity acquisition**, not merely registration. Preserve zero-payment behavior and reject a reduced rate rather than clamp or silently accept it.

Use actual protocol entrypoints in the reproduction, not only a direct-call unit test that cannot occur through the manager.

### 3. Reconcile signed deltas, settlement, custody and liabilities

Build an independent per-currency ledger for the router/trader, hook, manager, locker and collector. For manager account deltas and caller `BalanceDelta`, negative means the account owes the manager; positive means the manager owes the account. For the pinned `IHooks` swap return deltas, positive means the hook is owed/has taken currency; negative means the hook owes/has sent currency. Swap `amountSpecified < 0` is exact input and `> 0` exact output. `BeforeSwapDelta` packs specified/unspecified currency amounts, **not** token0/token1. Derive their mapping to currency0/currency1 from request sign and direction; do not confuse request sign, hook entitlement and final trader wallet changes. Confirm these conventions against the actual pinned core interfaces before evaluating a different dependency revision.

Exercise both directions × exact input/output × each declared `InputToken`/`QuoteOnly` mode, including free and small rounded-to-zero fees. Derive which currency is specified/unspecified on each path; `QuoteOnly` is not always the input currency and supporting both modes does not charge both at once.

For each swap/collection/donation sequence, assert:

- Real trader wallet changes agree with returned swap deltas, charged hook fees, and router limits. A quote or `feeRate()` preview alone does not prove execution receipts.
- The rate freezes before checkpointing/observer updates; the paired swap context matches pool, sender and original parameters, cannot be overwritten or reused, and is consumed exactly once.
- Specified-currency precharges enforce the base's required exact fill; unspecified-currency fees use actual filled volume. Test restrictive price limits and partial-fill paths rather than assuming requested and filled amounts coincide.
- Successful unlock ends with cleared account/currency deltas for all participating accounts. The unlock invariant prevents unresolved manager debt; it does **not** prove fair pricing, correct recipient choice, or correct internal liability attribution.
- `pendingFees - settledFees` matches tracked manager-claim backing; tracked cash covers settled fee liabilities, and mint/burn/take/transfer changes are exact. Extra donated cash/claims cannot be counted as earned fees. Claim IDs must use canonical currency encoding without high-bit aliases.
- Signed headroom, checkpoint parking and aggregate liabilities stay bounded. Collection burns tracked claims before taking cash and pays treasury/collector exactly once. If manager cash is temporarily unavailable, exercise the documented `FeeSettlementRequired` failure/repayment path; no fictitious credit or principal fallback.
- Direct token transfers, manager donations, zero-delta liquidity pokes and accrued LP growth do not become redeemable hook-fee proceeds, even after repeated collection. Launch principal/positions remain in permanent custody; no added selector, approval or assembly path can release them.
- Treasury, collector, executor, owner/disposition and developer receipts reconcile to the independent ledger. Reject unauthorized recipients and prove no double author allocation.

Extend the reasoning in `LaunchDeltaAccountingFixture` rather than replacing actual wallet/claim evidence with emitted events or expected values copied from production helpers.

### 4. Attack arithmetic, slippage and economic boundaries

Read `LaunchHookFeeRateV2` and the submitted formula. Maintain a vector table of inputs, units, expected rate/fee, rounding, execution result and affected consumer. Use an independent exact-integer calculation as the oracle for expected values.

- Cover minimum = maximum, minimum/maximum zero, maximum `1_000_000`, zero/max sensitivity, smallest nonzero amounts, floor boundaries, fee headroom around `int128.max`, and signed minimum/maximum requests. Check negation of `int256.min`, narrowing casts, sign-extension, unchecked arithmetic and multiplication/division order. Invalid inputs must reject intentionally, not wrap into affordable prices.
- For custom policy math, test denominators of zero/one, tick extremes, negative ticks, decimal normalization, timestamp/cumulative boundaries, and each piecewise branch's neighbors. Check monotonicity only where the documented policy promises it. Assess profitable repeated dust/split trades and round trips, not just a single rounding discrepancy.
- Test zero active liquidity, out-of-range positions, no positions, first deposit, and tick/price manipulation before liquidity acquisition. Trace registrar/initialization/opening controls and actual router liquidity protections; do not assume atomic launch or a public periphery's checks without exercising the real path.
- Check trader maximum-input/minimum-output protection against **final hook-adjusted** execution amounts, including 100% fee, price-limit and exact-output failures. A frozen bounded rate is not a guaranteed execution quote.
- Where liquidity changes expose principal and accrued-fee deltas, test slippage on the intended principal amount separately from net accrued fees. Test positive net deltas with a costly deposit, negative returned deltas, and a zero-liquidity modification that realizes fees. Permanent launch custody does not eliminate slippage risk for any permitted external LPs.

Quantify value lost by trader/LP/owner/author under an executable adversarial sequence. A surprising rate is not a finding if it matches disclosed immutable terms; a mismatch between advertised and charged economics still needs receipts and a specific broken contract.

### 5. Explore reentrancy, cross-pool and routing reachability

Mark every external call, including token transfers/balance queries, locker checkpoints, collector/hub/core reads, oracle/config reads and derived-policy calls. Inspect state before and after each call. A view seam may still depend on adversarial external state; nonvirtual guards do not make arbitrary assembly or added functions safe.

Test same-pool nested actions, collection during swaps/checkpoints, read-only reentrancy into previews, and malicious callback returns/reverts. The locker has a deliberate checkpoint exception for authenticated **zero-delta** liquidity callbacks; show that nonzero or wrong-caller nested operations reject without disabling legitimate checkpointing.

General V4 hooks may serve many pools; this runtime must reject a second full key. Prove that rejection through manager operations, not just a helper. Also test a route touching another hook/pool with shared currencies, repeated visits to the bound pool, multiple actions in one unlock, and sequential same-block swaps. Net settlement in a singleton and pooled token balances do not authorize cross-pool liability attribution or reuse of pending swap state. Separate genuinely reachable routing/reentrancy from theoretical paths blocked by current manager rules or immutable topology.

### 6. Review oracles, signed permissions and external dependencies

**Oracle evidence.** Core-only hooks have no history and report oracle genesis as zero. For composition, follow authenticated genesis, quote-normalized tick orientation, per-block clamp, registered config/capacity snapshot, retained ring history, and stored versus extrapolated accumulators. Test pre-init/pre-genesis/evicted queries, genuine one/two-sample warm-up, same-timestamp/same-block observations, idle age, flat/falling movement and adversarial price manipulation. Cardinality is capacity, not mature lookback; do not fabricate samples. The observer runs after fee freezing, so a swap cannot set its own rate from its own observation. Evaluate clamp and sampling manipulation cost against actual policy impact; truncation is not a universal manipulation guarantee. Do not impose the reference dynamic formula on unrelated policies.

**Admission and signatures.** Read `LaunchImplementationRegistryV2` and its signature-library/domain implementation. Obtain a production authorization digest from the **target registry's `authorizationDigest`**, not a hand-written hash or file SHA256. Review chain/verifying-contract domain separation, profile/review/terms commitments, exact registration/envelope graph fields and economics, current author-controller identity, deadline, nonce consumption, and administrator-only submission. Exercise real EOA signatures and contract-signature validation where applicable, invalid/expired signatures, wrong signer/domain/chain/registry, changed commitments/recipients/graph, replay, and controller/payout changes. A relayer or administrator may submit an authorized payload but must not gain authority to substitute it. A stable author ID is not proof of consent from its current controller.

**Derived-policy swap passes.** Admission gates may use existing supported policy seams, including `_onBeforeSwap`, without modifying the approved base or its final callbacks/accounting. Review the concrete implementation and qualification capability before assuming a permission path exists: the base does not pass `hookData` as an observer argument, and `_onBeforeSwap` receives authenticated price/liquidity snapshots, not a buyer or signature. Trace the actual pass API or manager call-frame decoding, including `msg.data`/selector coupling where used, and how it binds to the swap; do not invent argument forwarding or add a companion deployment. If qualification cannot exercise that implementation, report the exact missing maintainer-owned harness capability separately.

For a concrete signed swap-pass policy, require these checks in addition to downstream registry author authorization:

- Independently reconstruct the policy's EIP-712 typed-data digest from its documented type/domain and signed fields; compare it to the implementation. Use valid EOA signatures and, where supported, a cryptographic ERC-1271 signer that validates that exact digest/signature. An always-return-magic mock proves neither signature security nor signer consent. Test invalid signatures, wrong signer, malformed encodings and contract-signer reverts/wrong magic values.
- Trace buyer, payer, recipient, manager callback sender, router, transaction origin and relayer separately. Identify which identity the signed pass authorizes and which identity consumes it. Exercise direct and actual routed swaps, relayed calls, changed buyer/recipient/router and nested calls. If the policy relies on `tx.origin`, document and test the resulting smart-wallet/relayer restrictions and whether an intervening contract can use the origin's pass; do not describe origin as authenticated callback ownership.
- Mutate domain name/version, chain ID and verifying hook address independently, as well as any signed pool, direction, amount bound, price/fee bound, nonce and deadline. Prove the signed intent cannot be transplanted to another hook/pool or a different trade; disclose fields intentionally left unbound and their consumer consequences.
- Test expiry boundaries, nonce reuse, front-running/pass consumption, duplicate use in one unlock, repeated routed hops and replay across transactions. Verify that a reverted swap/settlement rolls back nonce/pass consumption and leaves no usable stale pending context; successful execution consumes precisely the intended authorization. Any revocation or cancellation claim needs an exercised existing mechanism, not a newly invented privilege.
- Exercise exact-input and exact-output trades in both directions, amount-bound neighbors, restrictive price limits, actual partial fills and the base's specified-fee full-fill rejection. State whether authorization caps the requested amount, actual input paid or actual output delivered, and prove fees and retries cannot turn that definition into a bypass.
- Exercise pre-opening buys/sells and post-opening buys/sells against the policy's documented transition, including the opening boundary and any exempt direction. The base supplies no general admission gate: prove enforcement or deliberate permission in each phase, rather than assuming opening completion turns a derived gate on or off.
- Model signer loss, compromise and contract-signer validation changes. Quantify unauthorized trade access or lasting buyer liveness loss, and identify only recovery/revocation powers that actually exist. An immutable signer with no recovery is a disclosed trust/liveness boundary, not permission to add an upgrade, new administrator or sweep mechanism.

For reachable permit-enabled integrations, also test front-running/nonce consumption, revocation, expiry and relayer identity without treating a blanket catch-and-continue as authorization. Fixture author keys and fork-only registry administration prove only the exercised fixture flow, not the submitted author's production consent; a valid swap pass likewise does not confer registry admission. Never request or publish private keys or production admission signatures.

**Tokens, dependencies and privileged settings.** Record supported currency types and actual token/code assumptions; standard ERC20/WETH qualification does not establish support for fee-on-transfer, rebasing, ERC777-style callbacks, double-entry/native aliases, arbitrary decimals, false/no-return transfers, or pausable/blacklisting tokens. Trace exact-transfer checks and explain unsupported-token rejection versus recoverable liveness loss; do not silently broaden support. Assess malicious balance reads, reverting/empty-code dependencies, large returndata, gas exhaustion, oracle/config unavailability and dust/donation griefing. Measure attacker cost, persistence, which consumer is blocked, and whether safe retry/repayment is possible.

Inventory existing registry/admin, author-controller/payout, protocol-fee governance and dependency powers. Distinguish immutable creator settings from mutable external authority. Test economic/registry bounds, capacity limits, denied external liquidity and protocol fees being enabled; nonzero manager protocol fees intentionally halt swaps until cleared, so record this governance liveness dependency. Do not propose upgrades, new sweep/pause privileges or recipient controls as review fixes that violate catalogue invariants.

### 7. Qualify, reproduce, and report

After any fix, exercise the specific adversarial behavior and perform **fresh full qualification using `hook-qualification`** on the final artifact. Structure checks, compile success, an isolated fixture, and old CI evidence do not substitute for a new full run. New artifact/constructor/dependency changes invalidate prior artifact hashes and mined salts. Keep targeted test coverage and full qualification coverage separate; the standard launch scenario is not exhaustive bounds, arbitrary-token or policy proof.

Use `HookSmokeTest` / `HookLaunchFixture` for real launch/delta accounting, with the constructor descriptor selecting the actual reviewed artifact; never substitute candidate code with `vm.etch` or a deployment override. Inherited public nonvirtual `testSmoke*` checks are mandatory and unskippable. Review mutable setup and prerequisites as assumptions, not a sandbox; successful baseline tests cannot prove arbitrary-policy safety or signer consent. Add adversarial/formula/oracle/signature evidence in the contributor's separate policy `test/*.t.sol` suites. If the needed scenario cannot be expressed through existing configuration/prerequisite/hookData seams, identify the exact missing capability for a separate maintainer change; do not narrow the claimed review or modify shared infrastructure inside a hook submission. Retain genuine failed-check/RPC evidence and missing prerequisites rather than describing unexecuted checks as passed. Review compact provenance with the matching sources/tests; `--check-provenance` checks identity freshness, not current-chain behavior, and full credential-bearing logs remain local.

## Evidence-backed findings and private disclosure

Each finding should include:

1. Identifier/title, status (confirmed current defect, unconfirmed hypothesis, historical lesson, or accepted/disclosed trust risk), severity and rationale based on affected consumers, assets/value at risk, attacker permissions/cost and repeatability. Do not copy an upstream severity onto a different path.
2. Exact reviewed commit/working-tree/artifact and dependency scope, source path/symbol/lines, deployed or fork identity if used, and the violated repository/economic invariant.
3. Minimal reachable transaction sequence and reproduction command/test, preconditions, independent expected result versus observed balances/deltas/claims/receipts or availability. Link retained evidence and disclose fixture shortcuts. For denial of service, show the blocked legitimate action and persistence/recovery conditions; for economic loss, quantify whose value moves to whom.
4. Root cause, narrowly scoped fix preserving immutable pool-bound invariants, regression acceptance criterion, and observed retest/fresh qualification status. Separate suggested fixes and unrun tests from measured results.
5. Historical source/fix provenance where relevant and why it applies now, does not apply, or remains unestablished. Record coverage gaps and unsupported scenarios explicitly.

End the report with scope/assumptions, completed coverage, commands actually executed and pass/fail evidence, unresolved findings, missing checks, and residual trust/liveness risks. “No confirmed findings in the exercised scope” is not “secure,” and fixture proof is not production author authorization or an independent audit.

Follow `SECURITY.md`: report exploitable vulnerabilities privately through the repository's **Security → Report a vulnerability** page. Do not put exploit details, keys, sensitive artifacts or admission signatures in public PRs/issues or public CI logs. Treat submissions and artifacts as untrusted and run them only in disposable environments without credentials or wallet keys. Public `review.md`/PR evidence may describe non-sensitive coverage and limitations; coordinate private finding details and disclosure with maintainers.
