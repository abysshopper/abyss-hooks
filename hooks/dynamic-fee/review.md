# DynamicFeeHook

- Base and scope: `PoolBoundLaunchHookBaseV2`, with the unchanged `PoolBoundHookParametersV1` constructor. Only author-payment, Dynamic model and pure rate declarations are overridden; callbacks, custody, payees, oracle updates and accounting remain inherited. Dynamic swaps require zero LP fee; the trading fee is hook-only.
- Formula: let `M = maximumPips`, `S = sqrtPriceX96`, `L = activeLiquidity`, and `A = -amountSpecified` for the original exact-input request. The input virtual reserve is `R = floor(L * 2^96 / S)` for `zeroForOne`, otherwise `R = floor(L * S / 2^96)`. Let `B = floor(M / 5)`; the rate is `B + floor((M - B) * A / (R + A))`. Both reserve and rational uplift use full-precision multiplication/division with floor rounding, without token-decimal assumptions or added configuration.
- Boundaries: `M == 0` returns zero first. Exact output (`amountSpecified > 0`), zero liquidity, zero sqrt price or a zero floored reserve return `M` conservatively: eventual input is unknown for exact output. With a positive reserve, zero input returns `B`, a floored 20% baseline; `A == R` gives `B + floor((M - B) / 2)`. The rational uplift is monotone in `A` and below `M - B` for finite input, approaching that ceiling asymptotically. Thus rates remain in `[B, M]`, including fallbacks; integer flooring may place the baseline below exactly 20% of `M`.
- Arithmetic and context: the final base wrapper rejects `int256.min` and checks the result against the configured maximum. Valid pool prices bound virtual reserves to 192 bits, while `A <= int256.max`, so `R + A` fits `uint256`. The base authenticates the original signed request, direction, configured maximum, fee mode, pre-swap price and active liquidity, freezing the rate once before checkpoints. Both fee modes use the same schedule; post-swap balances never recompute it.
- Author payment: `authorFeeBps()` requires 500 bps of source-attributed owner proceeds after bounty through the existing V3 hub, independent of trading fees. No payee is added. A different frozen author allocation is rejected by inherited validation.
- Provenance: independently authored directly from the disclosed rational formula; no external fee-hook implementation was copied. MIT; dependency licenses remain applicable.
- Risks and qualification: virtual reserves describe active liquidity at the pre-swap price, not guaranteed full-fill depth across ticks; conservative fallback rates can equal the configured maximum. The complete inherited callbacks, constructor-created validation helper and full dependency graph still require review, including pure-seam liveness and overflow bounds. Canonical declared bounds and focused arithmetic tests are not exhaustive runtime qualification, production admission or author-control proof; this is a reference example with null author identity.
